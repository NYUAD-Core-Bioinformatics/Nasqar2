## Installation Options using Docker

In order to deploy NASQAR2 using the various Docker based installation option, please ensure you have already installed [Docker](https://www.docker.com/products/docker-desktop/)

### [Option 1: Pull Prebuilt Docker from Cloud](#option-1-pull-prebuilt-docker-from-cloud) (Recommended - Fastest)
Pull and run the complete NASQAR2 suite with all applications in a single Docker container. No building required - just pull and run!

### [Option 2: Build All-in-One Docker from Source](#option-2-build-all-in-one-docker-from-source)
Build the complete NASQAR2 Docker container with all applications from source code.

### [Option 3: Build Individual Docker Containers from Source](#option-3-build-individual-docker-containers-from-source)
Build and run specific NASQAR2 applications (e.g., DESeq2, DADA2, Seurat) as separate Docker containers from source. Useful for specific tools or resource optimization.

---

### Option 1: Pull Prebuilt Docker from Cloud

We provide prebuilt Docker images with all NASQAR2 applications bundled together. This is the fastest and easiest way to get started.

**Pull the image:**

```bash
docker pull nyuadcorebio/nasqarall:latest
```

**To run NASQAR2 on port 80:**

```bash
docker run -p 80:80 nyuadcorebio/nasqarall:latest
```

**To run NASQAR2 on a different port** (e.g., port 8083):

```bash
docker run -p 8083:80 nyuadcorebio/nasqarall:latest
```

Access via web browser at `http://localhost/` or `http://localhost:8083/` depending on the port used.

Run this way, NASQAR2 is a **public instance**: every dataset enters through browser upload and nothing on the host filesystem is visible to the applications. That is the right default for a shared server.

### Run as a private instance with your own data

When NASQAR2 serves only you, on a laptop or workstation in Docker, or in a Slurm job on HPC, you can run it as a **private instance**. Mount your data directory and set `NASQAR_DATA_ROOT` to where it appears inside the container; the applications then browse and read files in place instead of uploading them, and projects, states, and results are written back to host directories you choose, so they survive container restarts.

```bash
docker run -p 127.0.0.1:8083:80 \
  -v /path/to/nasqar2-private:/private \
  -v /path/to/nasqar2-private/data:/private/data:ro \
  -e NASQAR_PRIVATE_ROOT=/private \
  -e NASQAR_DATA_ROOT=/private/data \
  -e NASQAR_PROJECT_ROOT=/private/projects \
  -e R_LIBS_USER=/private/.runtime/R/library \
  -e NASQAR_DADA2_WORK_DIR=/private/.runtime/work/DADA2 \
  nyuadcorebio/nasqarall:latest
```

One folder holds everything: `data/` (mounted read-only on top, so the
applications can never write into it), `projects/<App>/<name>` for every run,
and a hidden `.runtime/` for the R library and scratch files. Browse dialogs
open at the top of that folder and show only `data` and `projects`, so a result saved by one application (a merged count
matrix, a Seurat object) can be picked as the input of another. Binding to
`127.0.0.1` keeps the private instance off the network; reach it from another
machine with `ssh -N -L 8083:localhost:8083 <host>`.

In a private instance the applications with data-root access show a **Browse…**
button next to the path box. It opens a server-side file browser that is limited
to the data root and only fills in the path; nothing is copied or uploaded.
Variant Annotation's **Install another reference genome** panel likewise appears
only when `R_LIBS_USER` points to a mounted library: a public instance has
nowhere persistent to install into, so visitors cannot trigger downloads.

The same variables work with an image built from source (`nasqar2-all`). Leave `NASQAR_PROJECT_ROOT` unset and the applications keep their results in temporary storage inside the container, discarded when it stops. Browser upload and download remain available in every mode.

**Projects.** With `NASQAR_PROJECT_ROOT` set, every NASQAR2 application keeps its work as a project, `projects/<App>/<name>`, holding the outputs, the caches, a `state.rds` with the inputs, settings and stage reached, and a human-readable `state.json` with the same settings plus a snapshot of every UI input at that moment, so the choices behind a result can be read without R (for a methods section, or to share with a colleague). Every figure or table you download is also kept in the project (`plots/` and `downloads/`), and the project panel shows a gallery of them. Each app's input tab has the same two controls: **Persistent project name** (or the app's existing project-name box) and **Restore an existing project**, which lists the projects of that app with their input, stage and date. Restoring reopens the project without recomputing: cached results are reused, and a restore is refused when the source data changed since the project was made. The older per-application variables (`NASQAR_DESEQ2_STATE_DIR`, `NASQAR_*_PROJECT_DIR`, `NASQAR_ATAC_CACHE_DIR`) are still honoured as overrides.

| Variable | Application | Purpose |
| --- | --- | --- |
| `NASQAR_PRIVATE_ROOT` | All NASQAR2 applications | The private folder as a whole; Browse dialogs start here |
| `NASQAR_DATA_ROOT` | All NASQAR2 applications | Read-only data directory inside it; input paths must lie under it or under the projects |
| `NASQAR_PROJECT_ROOT` | All NASQAR2 applications | Private-space projects, one folder per application and project name (`projects/<App>/<name>`), each restorable from the app |
| `NASQAR_DADA2_WORK_DIR` | DADA2 | Optional fast local scratch for temporary files |
| `R_LIBS_USER` | All | Writable R library, so packages installed on the fly survive container restarts |

Applications only accept paths under `NASQAR_DATA_ROOT`, so mount the narrowest directory that holds your inputs rather than your home directory.

**Example data.** To have something to try in every application's private-space input, populate the data folder once with small public data sets (pasilla RNA-seq, 10x pbmc3k, the mothur MiSeq SOP, SILVA references, and the ATAC-seq and VCF examples shipped with Bioconductor packages):

```bash
common/fetch-example-data.sh /path/to/nasqar2-private/data
```

It writes `data/examples/<App>/...` (about 140 MB, or 360 MB with the SILVA taxonomy references; `--skip-silva` leaves those out) and an `examples/README.md` naming each source. Downloads happen on the machine you run it on; the derived files (DESeq2 results for ORA/GSEA, a Seurat object for Monocle 3) are computed inside the NASQAR2 image, so Docker (or `--sif` for a Singularity image) must be available.

> **Do not set `NASQAR_DATA_ROOT` or the project directories on a public deployment.** Any user of the portal could then browse and read whatever is mounted there. Leave them unset and the instance stays upload-only.

On HPC the Slurm job script sets all of these for you; see the [HPC Deployment Guide](/quickstart/hpc).

### Option 2: Build All-in-One Docker from Source

Build the complete NASQAR2 Docker container with all applications from source code.

1. **Clone NASQAR2 Repository:**

```bash
git clone https://github.com/NYUAD-Core-Bioinformatics/Nasqar2.git
cd Nasqar2
```

2. **Build Docker Image:**

```bash
sh extract_data.sh  
docker build -t nasqar2-all .
```

3. **Run Docker Container:**

```bash
docker run -p 80:80 nasqar2-all
```

Access via web browser at `http://localhost/`

---

### Option 3: Build Individual Docker Containers from Source

Each NASQAR2 application can be run as a standalone Docker container. This is useful for running specific tools independently or reducing resource usage.

**Note**: Individual Docker containers are only available by building from source. Prebuilt images are not provided in the cloud repository.

### Available Applications

NASQAR2 includes the following applications that can be built individually:

- `animalcules` - Microbiome analysis
- `ATACseqQCShniy` - ATAC-seq quality control
- `ClusterProfShinyGSEA` - Gene Set Enrichment Analysis
- `ClusterProfShinyORA` - Over-Representation Analysis
- `dada2Shiny` - 16S/ITS amplicon sequencing analysis
- `DEBrowser` - Differential expression analysis browser
- `deseq2shiny` - DESeq2 differential expression analysis
- `GeneCountMerger` - Merge gene count matrices
- `monocle3` - Single-cell trajectory analysis
- `SeuratV5Shiny` - Single-cell RNA-seq analysis
- `tsar_nasqar` - Time series analysis

### Build Individual Docker from Source

1. **Clone NASQAR2 Repository:**

```bash
git clone https://github.com/NYUAD-Core-Bioinformatics/Nasqar2.git
cd Nasqar2
```

2. **Navigate to the specific application directory:**

**Example for DESeq2:**
```bash
cd deseq2shiny
```

**Example for DADA2:**
```bash
cd dada2Shiny
```

**Example for Seurat:**
```bash
cd SeuratV5Shiny
```

3. **Build the Docker image:**

```bash
docker build -t nasqar-deseq2 .
```

4. **Run the container:**

```bash
docker run -p 9001:3232 nasqar-deseq2
```

Access the application at `http://localhost:9001/`

## Local Installation with Anaconda

In order to deploy NASQAR2 using Conda, please ensure you have installed [Conda/MiniConda/Anaconda] on your system.

Run individual applications directly on your system without Docker. Each application has its own conda environment with specific dependencies.

### Prerequisites

- **Anaconda** or **Miniconda** installed on your system
- Download from [Anaconda](https://www.anaconda.com/products/distribution) or [Miniconda](https://docs.conda.io/en/latest/miniconda.html)

### Setup Application-Specific Environment

Each NASQAR2 application has its own `environment.yaml` file for creating an isolated conda environment.

**Example: Setting up DESeq2 application:**

1. **Clone NASQAR2 Repository:**

```bash
git clone https://github.com/NYUAD-Core-Bioinformatics/Nasqar2.git
cd Nasqar2
sh extract_data.sh  
```

2. **Navigate to the application directory:**

```bash
cd deseq2shiny
```

3. **Install mamba (if not already installed):**

```bash
conda install -c bioconda -c conda-forge mamba -y
```

4. **Create application-specific conda environment:**

```bash
mamba env create -f environment.yaml
```

5. **Activate the environment:**

```bash
conda activate deseq2shiny
```

6. **Navigate to the src directory:**

```bash
cd src
```

7. **Run the application:**

```bash
R -e "shiny::runApp('.', port = 9001, host = '0.0.0.0')"
```

Access the application at `http://localhost:9001/`

### Running Different Applications

**Example: Setting up DADA2 application:**

```bash
cd Nasqar2/dada2Shiny
mamba env create -f environment.yaml
conda activate dada2Shiny
cd src
R -e "shiny::runApp('.', port = 9002, host = '0.0.0.0')"
```

**Example: Setting up Seurat application:**

```bash
cd Nasqar2/SeuratV5Shiny
mamba env create -f environment.yaml
conda activate SeuratV5Shiny
cd src
R -e "shiny::runApp('.', port = 9003, host = '0.0.0.0')"
```

**Note**: Each application maintains its own isolated environment to avoid dependency conflicts.
