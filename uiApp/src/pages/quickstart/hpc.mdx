## HPC deployment

NASQAR2 can run as an unprivileged Singularity container inside a Slurm
compute allocation. The deployment starts the portal and all analytical
services on one compute node, stores writable state outside the read-only
container image, and reports the SSH tunnel needed to open the portal.

> Run NASQAR2 through `sbatch`.

## Resource model

The supplied job requests one task, 16 CPU cores, 32 GB memory, and eight
hours. Adjust these values in `hpc/slurm/nasqar2.sbatch` for the dataset and
local scheduling policy.

| Resource | Default |
| --- | --- |
| Slurm tasks | 1 |
| CPU cores | 16 |
| Memory | 32 GB |
| Wall time | 8 hours |
| Portal port | Job-specific value from 20000 to 39999 |

## Build the Singularity image

Build the all-in-one Docker image (the Singularity definition bootstraps from
the `nasqar2-all:latest` tag), then create the SIF:

```bash
docker build -t nasqar2-all:latest .
./hpc/build-sif.sh
```

The default output is `hpc/build/nasqar2.sif`. The Singularity build can
require approximately 25 GB of temporary space. Redirect its temporary and
cache directories when `/tmp` is too small:

```bash
mkdir -p /data/nasqar2-build/{tmp,cache}
TMPDIR=/data/nasqar2-build/tmp \
SINGULARITY_TMPDIR=/data/nasqar2-build/tmp \
SINGULARITY_CACHEDIR=/data/nasqar2-build/cache \
./hpc/build-sif.sh /data/nasqar2-build/nasqar2.sif
```

The `docker-daemon` bootstrap exports the image through the Docker daemon,
which stages it under `/var/lib/docker/tmp`. If that filesystem has less than
about 15 GB free the build fails with `no space left on device` even when the
directories above point elsewhere. In that case stream the container
filesystem into a sandbox directory and build from it instead:

```bash
mkdir -p /data/nasqar2-build/sandbox
cid=$(docker create nasqar2-all:latest)
docker export "$cid" | tar -x -C /data/nasqar2-build/sandbox
docker rm "$cid"
sed 's#^Bootstrap: docker-daemon$#Bootstrap: localimage#; s#^From: .*#From: /data/nasqar2-build/sandbox#' \
  hpc/singularity/nasqar2-local.def > /data/nasqar2-build/nasqar2-sandbox.def
singularity build --fakeroot --force /data/nasqar2-build/nasqar2.sif /data/nasqar2-build/nasqar2-sandbox.def
```

Run the `singularity build` from the repository root so the definition's
`%files` entry resolves. The resulting SIF is identical in content; only the
Docker metadata (which the definition re-creates) is not carried over.

## Install in scratch

The example below uses `$SCRATCH/nasqar2`. Replace the login host and paths
with values appropriate for the HPC system.

```bash
ssh USER@LOGIN_HOST \
  'mkdir -p "$SCRATCH/nasqar2"/{bin,images,slurm,runs}'

rsync -ah --partial hpc/build/nasqar2.sif \
  USER@LOGIN_HOST:/path/to/scratch/nasqar2/images/nasqar2.sif
rsync -ah hpc/bin/nasqar2-hpc \
  USER@LOGIN_HOST:/path/to/scratch/nasqar2/bin/
rsync -ah hpc/slurm/nasqar2.sbatch \
  USER@LOGIN_HOST:/path/to/scratch/nasqar2/slurm/
```

## Submit and connect

```bash
ssh USER@LOGIN_HOST \
  'cd "$SCRATCH/nasqar2/slurm" && sbatch nasqar2.sbatch'
```

After the job starts, read its connection file:

```bash
cat "$SCRATCH/nasqar2/runs/JOB_ID/connection.txt"
```

Run the reported tunnel command on the workstation. Keep that terminal open:

```bash
ssh -N -L PORT:COMPUTE_NODE:PORT USER@LOGIN_HOST
```

Then open `http://localhost:PORT`. The tunnel command intentionally appears to
remain active; it is forwarding traffic until stopped with `Ctrl+C`.

## Persistent and temporary storage

| Data | Default location |
| --- | --- |
| Per-job runtime, logs, uploads, and exchange files | `$SCRATCH/nasqar2/runs/JOB_ID` |
| Private-space projects of every application (`projects/<App>/<name>`, each with its outputs, caches and a `state.rds` for restoring) | `$SCRATCH/nasqar2/projects` (`NASQAR2_PROJECTS`) |
| Private R library | `$SCRATCH/nasqar2/r-library/R-4.3` |

Input data are mounted read-only from `NASQAR2_DATA_ROOT`, which defaults to
`$SCRATCH`. Applications validate requested paths against that root. Generated
files are written to the job runtime or persistent project directories, not
beside the source data.

Override storage locations at submission:

```bash
NASQAR2_DATA_ROOT=/scratch/USER/project \
NASQAR2_R_LIBRARY=/scratch/USER/project/r-library \
sbatch nasqar2.sbatch
```

Variant Annotation streams filtered records to disk and annotates them in
chunks of `NASQAR_VARIANT_ANNOTATION_CHUNK` records (default 50,000), so a
cohort-sized VCF runs in bounded memory. Raise the chunk size on a node with
plenty of memory to trade RAM for speed, or lower it on a small allocation:
`NASQAR_VARIANT_ANNOTATION_CHUNK=100000 sbatch nasqar2.sbatch`.

## Applications with private-instance data access

A Slurm job is one form of NASQAR2 private instance: the portal serves a single
user, so it can read that user's files in place and keep results permanently on
the host filesystem instead of round-tripping them through the browser. The job
script enables this by setting `NASQAR_DATA_ROOT` and the per-application
project, state, and cache directories listed above. The same mechanism works
for Docker on a workstation; see
[Run as a private instance](/quickstart/installation#run-as-a-private-instance-with-your-own-data).

- **ATACseqQC** loads BAM/BAI pairs directly from the allowed data root and
  caches chromosome-, genome-, and motif-specific results.
- **DESeq2Shiny** saves and restores application states as projects in the
  private space while retaining browser download and upload.
- **DADA2** loads FASTQ files directly, processes temporary files in node-local
  storage, caches parameter-aware results, and writes persistent projects.
- **Seurat v5** loads count matrices or Seurat objects from the data root and
  writes project outputs to persistent scratch.
- **Monocle 3** loads Seurat objects from the data root and writes trajectory
  outputs to persistent scratch.
- **DESeq2Shiny**, **ClusterProfShinyORA**, **ClusterProfShinyGSEA**, **Gene Count
  Merger** and **mergeFPKMs** read their count or result tables, or a selection
  of per-sample count files, in place from the data root.
- **Variant Annotation** reads VCF files in place from the data root, writes a
  bgzip-compressed and indexed copy only when needed, and keeps filtered VCFs,
  annotation tables, and caches in persistent projects.

DADA2, Seurat v5, Monocle 3, and Variant Annotation derive worker availability
from `SLURM_CPUS_PER_TASK`. Other modules remain available in the same all-in-one
portal and take their input through browser upload.

## Install additional reference genomes

Variant Annotation ships human hg38 and hg19 and can install other species
(mouse, rat, zebrafish, fruit fly, nematode, yeast, chicken, pig, cow, dog,
rhesus macaque, chimpanzee) into the private R library, `NASQAR2_R_LIBRARY`
(default `$SCRATCH/nasqar2/r-library/R-4.3`). Compute nodes usually have no
internet access, so the in-app **Install** button fails there. The app then
shows a ready-to-run command, with the packages for the chosen genome filled
in, under **No internet on this server?**. Run it once on a login node; it
installs into the same library the job mounts, so the genome is available in
this and every later job. For mouse mm39 it is:

```bash
module load singularity
singularity exec --cleanenv \
  --bind $SCRATCH/nasqar2/r-library/R-4.3:/runtime/R/library \
  --env R_LIBS_USER=/runtime/R/library \
  $SCRATCH/nasqar2/images/nasqar2.sif \
  /opt/conda/envs/merged_env/bin/Rscript -e 'options(timeout = 7200); BiocManager::install(c("BSgenome.Mmusculus.UCSC.mm39", "TxDb.Mmusculus.UCSC.mm39.knownGene", "org.Mm.eg.db"), lib = "/runtime/R/library", update = FALSE, ask = FALSE)'
```

Installing packages is light enough for a login node. The `timeout` option matters: BSgenome
tarballs are up to 1 GB and R's default 60-second download limit aborts them.

## Stop a job

```bash
scancel JOB_ID
```

Stopping the Slurm job closes the portal. Persistent caches, states, and
project outputs remain available to later jobs.
