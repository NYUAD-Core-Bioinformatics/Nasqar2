## HPC deployment

NASQAR2 can run as an unprivileged Singularity container inside a Slurm
compute allocation. The deployment starts the portal and all analytical
services on one compute node, stores writable state outside the read-only
container image, and reports the SSH tunnel needed to open the portal.

> Run NASQAR2 through `sbatch`.

## Resource model

The supplied job requests one task, 16 CPU cores, 32 GB memory, and eight
hours. Adjust these values in `hpc/slurm/nasqar2.sbatch` for the dataset and
local scheduling policy.

| Resource | Default |
| --- | --- |
| Slurm tasks | 1 |
| CPU cores | 16 |
| Memory | 32 GB |
| Wall time | 8 hours |
| Portal port | Job-specific value from 20000 to 39999 |

## Build the Singularity image

Build the all-in-one Docker image, then turn it into a SIF:

```bash
docker build -t nasqar2-all:latest .
./hpc/build-sif.sh
```

Run both commands from the repository root. The SIF is written inside the
repository, to `hpc/build/nasqar2.sif`, wherever the script is run from
(pass another path as the first argument to change that). The build needs
about 25 GB of temporary space, also under `hpc/build`; set
`NASQAR2_BUILD_DIR` to use a larger filesystem instead.

## Install on the cluster filesystem

NASQAR2 keeps everything it needs on the cluster under one persistent,
writable directory, `NASQAR2_HOME`. Any space the site provides works: a
scratch area, a project or lab allocation, or your home directory, as long as
it is visible from the compute nodes and large enough for the image (about
10 GB) plus your projects. The job script defaults to `$SCRATCH/nasqar2` on
clusters that define `SCRATCH` and to `$HOME/nasqar2` elsewhere; set
`NASQAR2_HOME` to use another location. The example below uses
`/path/to/nasqar2` as a placeholder; replace it and the login host with your
own values.

```bash
ssh USER@LOGIN_HOST \
  'mkdir -p /path/to/nasqar2/{bin,images,slurm,runs}'

rsync -ah --partial hpc/build/nasqar2.sif \
  USER@LOGIN_HOST:/path/to/nasqar2/images/nasqar2.sif
rsync -ah hpc/bin/ \
  USER@LOGIN_HOST:/path/to/nasqar2/bin/
rsync -ah hpc/slurm/nasqar2.sbatch \
  USER@LOGIN_HOST:/path/to/nasqar2/slurm/
```

The job script loads a module named `singularity`; if your cluster names it
differently (for example `apptainer` or `singularity/4.2.0`), set
`NASQAR2_SINGULARITY_MODULE` at submission.

## Submit and connect

```bash
ssh USER@LOGIN_HOST \
  'cd /path/to/nasqar2/slurm && NASQAR2_HOME=/path/to/nasqar2 sbatch nasqar2.sbatch'
```

`NASQAR2_HOME` can be omitted when the install lives at the default location.

After the job starts, read its connection file:

```bash
cat /path/to/nasqar2/runs/JOB_ID/connection.txt
```

Run the reported tunnel command on the workstation. Keep that terminal open:

```bash
ssh -N -L PORT:COMPUTE_NODE:PORT USER@LOGIN_HOST
```

Then open `http://localhost:PORT`. The tunnel command intentionally appears to
remain active; it is forwarding traffic until stopped with `Ctrl+C`.

## Persistent and temporary storage

All locations are relative to `NASQAR2_HOME` unless overridden:

| Data | Default location | Override |
| --- | --- | --- |
| Per-job runtime, logs, uploads, and exchange files | `$NASQAR2_HOME/runs/JOB_ID` | `NASQAR2_RUNTIME_DIR` |
| Private-space projects of every application (`projects/<App>/<name>`, each with its outputs, caches and a `state.rds` for restoring) | `$NASQAR2_HOME/projects` | `NASQAR2_PROJECTS` |
| Private R library | `$NASQAR2_HOME/r-library/R-4.3` | `NASQAR2_R_LIBRARY` |

Input data are mounted read-only from `NASQAR2_DATA_ROOT`, which defaults to
the directory containing `NASQAR2_HOME` (with the default install, your
scratch or home space). Applications validate requested paths against that
root. Generated files are written to the job runtime or persistent project
directories, not beside the source data.

Override storage locations at submission:

```bash
NASQAR2_HOME=/path/to/nasqar2 \
NASQAR2_DATA_ROOT=/path/to/sequencing-data \
NASQAR2_R_LIBRARY=/path/to/shared/r-library \
sbatch nasqar2.sbatch
```

Variant Annotation streams filtered records to disk and annotates them in
chunks of `NASQAR_VARIANT_ANNOTATION_CHUNK` records (default 50,000), so a
cohort-sized VCF runs in bounded memory. Raise the chunk size on a node with
plenty of memory to trade RAM for speed, or lower it on a small allocation:
`NASQAR_VARIANT_ANNOTATION_CHUNK=100000 sbatch nasqar2.sbatch`.

## Example data

To try each application before pointing it at your own files, populate the
data root once from a login node (it downloads public data sets and derives a
few files inside the image; about 360 MB, `--skip-silva` for 140 MB):

```bash
common/fetch-example-data.sh /path/to/data --sif /path/to/nasqar2/images/nasqar2.sif
```

`/path/to/data` is the directory the job mounts as `NASQAR2_DATA_ROOT` (by
default the directory containing `NASQAR2_HOME`). The files land in
`/path/to/data/examples/<App>/` with a README naming every source; pick them
from the Browse dialog of the matching application.

## Applications with private-instance data access

A Slurm job is one form of NASQAR2 private instance: the portal serves a single
user, so it can read that user's files in place and keep results permanently on
the host filesystem instead of round-tripping them through the browser. The job
script enables this by setting `NASQAR_DATA_ROOT` and the per-application
project, state, and cache directories listed above. The same mechanism works
for Docker on a workstation; see
[Run as a private instance](/quickstart/installation#run-as-a-private-instance-with-your-own-data).

- **ATACseqQC** loads BAM/BAI pairs directly from the allowed data root and
  caches chromosome-, genome-, and motif-specific results.
- **DESeq2Shiny** saves and restores application states as projects in the
  private space while retaining browser download and upload.
- **DADA2** loads FASTQ files directly, processes temporary files in node-local
  storage, caches parameter-aware results, and writes persistent projects.
- **Seurat v5** loads count matrices or Seurat objects from the data root and
  writes project outputs to the persistent project space.
- **Monocle 3** loads Seurat objects from the data root and writes trajectory
  outputs to the persistent project space.
- **DESeq2Shiny**, **ClusterProfShinyORA**, **ClusterProfShinyGSEA**, **Gene Count
  Merger** and **mergeFPKMs** read their count or result tables, or a selection
  of per-sample count files, in place from the data root.
- **Variant Annotation** reads VCF files in place from the data root, writes a
  bgzip-compressed and indexed copy only when needed, and keeps filtered VCFs,
  annotation tables, and caches in persistent projects.

DADA2, Seurat v5, Monocle 3, and Variant Annotation derive worker availability
from `SLURM_CPUS_PER_TASK`. Other modules remain available in the same all-in-one
portal and take their input through browser upload.

## Install additional reference genomes

Variant Annotation ships human hg38 and hg19 and can install other species
(mouse, rat, zebrafish, fruit fly, nematode, yeast, chicken, pig, cow, dog,
rhesus macaque, chimpanzee) into the private R library. Compute nodes usually
have no internet access, so the in-app **Install** button fails there; run the
helper once on a login node instead (the app shows the exact command under
**No internet on this server?**). For mouse mm39:

```bash
/path/to/nasqar2/bin/nasqar2-install-genome mm39
```

`nasqar2-install-genome --list` prints the catalog. The helper installs into
the same library the jobs mount, so the genome is available in this and every
later job. It honours the same `NASQAR2_HOME`, `NASQAR2_R_LIBRARY` and
`NASQAR2_SINGULARITY_MODULE` settings as the job script.

## Stop a job

```bash
scancel JOB_ID
```

Stopping the Slurm job closes the portal. Persistent caches, states, and
project outputs remain available to later jobs.
